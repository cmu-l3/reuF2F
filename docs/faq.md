# Frequently Asked Questions

## General Questions

### What is reuF2F?

ReuF2F is a benchmark for evaluating coding agents on open mathematical problems from undergraduate research formalized in Lean. Each problem is a conjecture or an expressly open problem from a paper or report produced in an undergraduate research program, formalized as a Lean 4 theorem whose proof is `sorry`.

### Which datasets are available?

ReuF2F has one dataset, `test.jsonl` at the repository root, with 244 problems: 45 each in discrete mathematics, number theory, algebra, geometry and topology, and analysis, plus 19 in other areas. See the [datasets guide](guides/datasets.md).

### Why are there two directions?

The problems are open, so the expected answer is not known for certain. A model may prove the original theorem (the proof) or its full negation `<declaration>_neg` (the refutation). Both are checked in the same run.

### How does the evaluation work?

The evaluation process:

1. Starts a fresh Docker container from the shared Lean image
2. Applies the model's generated patch to the task project
3. Runs Comparator on the proof and the refutation concurrently
4. Parses the `PASSED`/`FAILED` status line for each direction

### What counts as resolved?

A task is resolved when Comparator accepts either direction: the submitted theorem matches the trusted statement and definitions, the proof uses only the axioms `propext`, `Quot.sound` and `Classical.choice`, and both the Lean kernel and nanoda accept it.

### What metrics are reported?

Key metrics include:

- **Total instances**: Number of instances in the dataset (after `-i`)
- **Instances submitted**: Number of instances the model attempted
- **Instances completed**: Number of instances that completed the evaluation process
- **Instances resolved**: Number of instances where the proof or the refutation was accepted
- **Instances unresolved**: Number of instances where the evaluation completed but neither direction was accepted
- **Instances with empty patches**: Number of instances where the model returned an empty patch
- **Instances with errors**: Number of instances where the evaluation encountered errors
- **Resolution rate**: Resolved instances divided by total instances

## Installation and Setup

### What are the Docker requirements?

Docker must run `linux/amd64` images and provide Buildx to build them. On an ARM machine, such as an M-series Mac, the image runs under emulation. See the [Docker setup guide](guides/docker_setup.md).

### How much disk space and memory do I need?

The shared image is about 15GB, and Docker Desktop may use several times that on disk while pulling and unpacking it. Each worker runs two Comparator processes at once, so memory and CPU needs grow with `-j`.

### How can I save disk space when using Docker?

Use these commands to clean up Docker resources:
```bash
# Remove unused containers
docker container prune

# Remove unused images
docker image prune
```

The harness removes each task container after evaluation and reuses the one shared image for every task.

## Using the Benchmark

### How do I run evaluations on my own model?

Generate predictions in the required format, for example with [Leanimum-agent](https://github.com/cmu-l3/Leanimum-agent), and run the evaluation harness on that file:
```bash
leani-extra reuf2f --subset test.jsonl -m <model> -o <output_dir>
reuf2f eval test.jsonl -p <output_dir>/preds.json --run-id my_run
```

### Can I run evaluations without using Docker?

No. Docker is required for consistent evaluation environments. This ensures that the evaluation is reproducible across different systems.

### How can I speed up evaluations?

- Evaluate selected instances with `-i`
- Increase parallelism with `-j`, within your CPU and memory limits

### What format should my model's output be in?

Your model should produce a patch that `git apply` can apply to the task project, whose task file is `<instance_id>.lean`. We recommend the diff generated by `git diff`. See [Prediction Format](guides/evaluation.md#prediction-format).

### Why isn't my evaluation re-running when I change the patch?

The evaluation harness caches results by `run_id`, model name and `instance_id`. It does not consider the patch content when checking the cache. If an instance already has a `report.json` under the run, it is skipped.

To re-evaluate an instance with a different patch, you must use a different `run_id`. For example:
```bash
# First evaluation
reuf2f eval test.jsonl \
    --predictions predictions_v1.jsonl \
    --run-id my_run_v1

# Re-evaluation with different predictions (must use different run_id)
reuf2f eval test.jsonl \
    --predictions predictions_v2.jsonl \
    --run-id my_run_v2
```

## Troubleshooting

### My evaluation is stuck or taking too long

Each task's `eval.sh` is limited by `-t` (default 7200 seconds). A task that exceeds it gets no report and is counted as an error. Try:
- Reducing the number of parallel workers
- Raising `-t`
- Checking Docker resource limits
- Making sure you have enough disk space

### Docker build is failing with network errors

Make sure your Docker network is properly configured and you have internet access. You can try:
```bash
docker network ls
docker network inspect bridge
```
